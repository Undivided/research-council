# R0.5-009 — Terminal-State Atomicity

## Question

Can Research Council prevent a process interruption during final run
terminalization from leaving durable state that falsely represents a logical
run as either incomplete or completely finalized?

## Problem

R0.5 currently persists several independently durable objects near the end of
a successful run:

- final agent outcome
- whole-run terminal state
- final human-readable run record

These objects are written separately.

A process failure between writes may produce a durable combination that is
internally inconsistent.

Examples include:

    all 11 successful outcomes exist
    but run state still says running

or:

    run state says completed
    but final run record does not exist

R0.5-006 protects explicit catchable process interruption during agent
execution.

R0.5-007 protects safe resumption of explicitly interrupted runs.

R0.5-008 protects exclusive ownership during local resume execution.

None yet defines the durability semantics of a crash during terminal
multi-file persistence.

## Required Distinction

    logical Council completion
    !=
    all terminal files happened to be written

and:

    terminal state visible
    =>
    required terminal durable objects are already complete

## Required Property

The system must not publish a terminal whole-run state until all durable
objects required by that terminal state are safely available.

A reader observing:

    run_status: completed

must be able to rely on the terminal durable representation being complete.

## Candidate Mechanism

Use publish-last semantics.

Prepare terminal artifacts first using temporary files.

Only after all prerequisite durable files are complete should the canonical
whole-run terminal state be atomically replaced.

Where appropriate, use same-filesystem atomic rename.

The exact implementation must be determined from the existing persistence
order before modifying runtime code.

## Success Criteria

A deterministic control must interrupt execution at each relevant
terminalization boundary.

For each interruption point, durable state must remain semantically valid.

The experiment must prove that no observable state exists where:

- run status is completed but the required final run record is absent
- terminal state claims more completed agents than durable successful outcomes
- a partially written canonical terminal state is visible
- a partially written final run record is treated as canonical
- retry/recovery duplicates institutional actions

A normal uninterrupted run must remain:

    run_status: completed
    reason: success
    attempted_agents: 11
    completed_agents: 11

with exactly eleven successful outcomes and one final run record.

## Non-Goals

R0.5-009 does not attempt to provide:

- filesystem-wide transactions
- database transactions
- distributed consensus
- distributed locking
- recovery from storage-device corruption
- durability against filesystem implementations that violate rename guarantees
- generalized event sourcing
- automatic replay of arbitrary historical writes

# R0.5-006 Interrupted Run Durability

## Question

Can the Research Council durably distinguish an actively executing Council run
from a run whose process terminated unexpectedly before normal runtime failure
or completion handling occurred?

## Motivation

R0.5-005 established durable whole-run state:

    running
    failed
    completed

The runtime updates that state during normal execution.

However, abnormal process termination can occur outside normal control flow.

Examples include:

- user interruption
- shell termination
- Ollama process termination
- system shutdown
- process crash
- external SIGTERM

In such a case, the last durable state may remain:

    run_status: running
    reason: in_progress

even though no Council process is still executing.

Therefore:

    durable state says running
    !=
    run is necessarily active

## Required Distinction

R0.5-006 must distinguish:

    active execution

from:

    interrupted execution

without requiring a later observer to guess solely from file age or missing
artifacts.

## Proposed Run State Extension

Add an interrupted terminal state:

    run_status: interrupted

Initial machine-readable reason:

    process_interrupted

The existing states remain:

    running
    failed
    completed

## Normal Completion

Normal R0.5-005 behavior remains unchanged.

A successful run ends:

    run_status: completed
    reason: success

A terminating runtime-controlled agent failure ends:

    run_status: failed
    reason: agent_failure

## Interrupted Execution

When the shell receives a supported termination signal while a Council run is
active, the runtime should persist:

    run_status: interrupted
    reason: process_interrupted
    current_agent: <agent-or-null>
    failed_agent: null

Existing counters remain unchanged at their latest durable values.

For example:

    attempted_agents: 2
    completed_agents: 1

means the second agent had begun but had not completed.

## Signal Handling

The experiment should initially cover catchable termination signals only.

Candidate signals:

    INT
    TERM
    HUP

The handler must:

1. preserve the current run state
2. mark the run interrupted
3. retain the current agent
4. avoid falsely marking the current agent as a normal R0.5-004 failure
5. terminate execution

The model does not choose this state.

## Important Limitation

SIGKILL cannot be trapped.

Power loss and kernel/process failure may also prevent final state persistence.

Therefore R0.5-006 does not claim perfect crash recovery.

It tests whether interruptions that reach the runtime can become explicit
durable state.

Uncatchable failures remain a separate problem.

## Causal Control

Baseline:

    process interrupted
    ->
    state may remain running
    ->
    future observer must infer abandonment

Experimental condition:

    process interrupted with catchable signal
    ->
    state becomes interrupted
    ->
    current agent and counters remain durable

The underlying interruption is unchanged.

Only system-owned durable state differs.

## Success Criteria

PASS requires:

- a run begins in running state
- a catchable interruption produces run_status: interrupted
- reason is machine-readable
- current agent remains explicit
- attempted-agent count remains correct
- completed-agent count remains correct
- no later agents are attempted
- no false successful final run record is created
- R0.5-004 agent outcomes already completed remain intact
- partially executing agent is not falsely labeled as normally failed
- R0.5-005 normal failed/completed behavior remains unchanged
- R0.5-003 artifact semantics remain unchanged
- R0.5-002 disposition semantics remain unchanged
- interrupted-run state does not enter canonical knowledge

## Non-Goals

R0.5-006 does not provide:

- automatic restart
- workflow resumption
- replay
- retry
- SIGKILL recovery
- power-loss recovery
- heartbeat monitoring
- distributed leases
- process supervision

Those are later concerns.

## Architectural Principle

A process ending unexpectedly should not force the institution to pretend that
execution is still occurring.

## Status

Experiment defined.

No runtime implementation yet.

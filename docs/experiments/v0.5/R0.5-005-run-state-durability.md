# R0.5-005 Run-State Durability

## Question

Can the Research Council durably represent the outcome of an entire Council
run, including partial and failed runs, without requiring reconstruction from
agent outcome files, missing artifacts, or terminal output?

## Motivation

R0.5-004 established durable per-agent operational state.

For every attempted agent, the runtime can distinguish:

    invocation_status
    artifact_status
    agent_status

However, the state of the Council run itself remains implicit.

A future observer may need to infer whether a run:

- completed successfully
- stopped on an agent failure
- completed with a nonfatal agent failure
- was interrupted before all agents were attempted

from:

- number of outcome records
- missing agent records
- presence or absence of a final run record
- terminal output
- filesystem state

Run outcome should be first-class.

## Required Distinction

Agent outcome is not run outcome.

For example:

    archivist:
        agent_status: failed

does not necessarily imply:

    run_status: failed

because the current Archivist validation path may allow execution to continue.

Likewise:

    judge:
        agent_status: failed

currently terminates the Council run.

The run record must state this distinction explicitly.

## Proposed Run State

Each Council invocation receives one system-owned run identity before any agent
is attempted.

A machine-readable run-state record should exist for that identity.

Minimum fields:

    type: council_run_state
    run_id: <run identity>
    project: <project>
    run_status: <status>
    reason: <machine-readable reason>
    current_agent: <agent-or-null>
    failed_agent: <agent-or-null>
    attempted_agents: <count>
    completed_agents: <count>
    total_agents: <count>

Initial allowed run states:

    running
    completed
    failed

Initial machine-readable reasons:

    in_progress
    success
    agent_failure

The runtime owns all fields.

Models do not determine run state.

## Initial Record

Before the first agent is attempted:

    run_status: running
    reason: in_progress
    current_agent: null
    failed_agent: null
    attempted_agents: 0
    completed_agents: 0
    total_agents: 11

## During Execution

Before attempting an agent:

    current_agent: <agent>

    attempted_agents is incremented

After successful completion of an agent:

    completed_agents is incremented

The run-state record must remain durable throughout execution rather than being
created only after successful completion.

## Successful Completion

After all agents finish:

    run_status: completed
    reason: success
    current_agent: null
    failed_agent: null
    attempted_agents: 11
    completed_agents: 11
    total_agents: 11

## Terminating Agent Failure

If Judge fails after promotion:

    run_status: failed
    reason: agent_failure
    current_agent: judge
    failed_agent: judge

The record must remain available after the shell process exits.

Agents later in the sequence are explicitly known to have not been attempted
because:

    attempted_agents < total_agents

Their absence does not have to carry that meaning alone.

## Nonfatal Agent Failure

If an Archivist operation fails but the existing runtime continues:

    archivist agent_status: failed

does not automatically imply:

    run_status: failed

The Council may continue to Librarian and reach:

    run_status: completed

This distinction must remain explicit.

## Storage

Proposed location:

    projects/<project>/runs/state-<RUN_ID>.yaml

This is operational project evidence.

It does not belong in canonical:

    knowledge/entries/

## Required Sequence

    create RUN_ID
    ->
    create run-state record: running
    ->
    attempt agents
    ->
    continuously update run state
    ->
    agent outcomes recorded by R0.5-004
    ->
    terminating failure:
        persist run failure
        exit
    ->
    successful end:
        persist run completion
        create normal human-readable run record

## Causal Control

Baseline:

    Judge failure
    ->
    nine outcome records
    ->
    no final run record
    ->
    terminal error

A later observer infers that the run failed at Judge.

Experimental condition:

    Judge failure
    ->
    nine outcome records
    ->
    durable run-state record explicitly states:
        run_status: failed
        failed_agent: judge
        attempted_agents: 9

The underlying failure is unchanged.

Only durable system-owned run state differs.

## Success Criteria

PASS requires:

- run identity exists before the first agent
- run-state record exists before the first model invocation
- running state is machine-readable
- current agent is machine-readable during execution
- attempted-agent count is explicit
- completed-agent count is explicit
- terminating failure is explicitly recorded
- failed agent is explicitly recorded
- successful completion is explicitly recorded
- nonfatal agent failure does not incorrectly force failed run state
- agents never attempted can be distinguished from attempted failures
- models do not determine run state
- no natural-language inference determines run state
- R0.5-004 agent outcomes remain unchanged
- R0.5-003 artifact boundaries remain unchanged
- R0.5-002 disposition remains unchanged
- run-state records do not enter canonical knowledge

## Non-Goals

R0.5-005 does not add:

- retry behavior
- workflow resumption
- checkpoints for restarting execution
- distributed workers
- scheduling
- process supervision
- crash recovery guarantees
- event sourcing

Those may follow later.

This experiment only makes whole-run state durable and explicit.

## Architectural Principle

A run should not have to finish successfully before the system can remember
that the run existed.

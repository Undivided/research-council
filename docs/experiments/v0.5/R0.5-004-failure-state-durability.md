# R0.5-004 Failure-State Durability

## Question

Can the Research Council durably record the outcome of each agent operation,
including failures, without requiring later inference from missing artifacts,
terminal output, or filesystem state?

## Motivation

R0.5-003 established a structural distinction between:

    raw model generation

and:

    validated cognitive artifact

A malformed model generation is preserved under `raw/` and correctly prevented
from entering `analysis/`.

However, after such a failure, a future observer may still need to infer what
happened from:

- the existence of a raw file
- the absence of an analysis file
- an incomplete run directory
- terminal output
- shell exit status

Absence should not carry institutional meaning.

The system should explicitly record whether an agent invocation succeeded,
whether an artifact was promoted, and why processing stopped.

## Required Distinctions

R0.5-004 must keep separate:

    invocation outcome

    artifact outcome

and:

    complete agent-operation outcome

For example:

    invocation_status: succeeded
    artifact_status: rejected_at_boundary

is different from:

    invocation_status: failed
    artifact_status: not_created

A successful model call does not imply a valid institutional artifact.

## Proposed Agent Outcome Record

The runtime should produce a machine-readable record for each attempted agent.

Minimum fields:

    type: agent_outcome
    run_id: <system-owned run identity>
    agent: <agent>
    invocation_status: <status>
    artifact_status: <status>
    agent_status: <status>
    reason: <machine-readable reason>
    raw_artifact: <path-or-null>
    promoted_artifact: <path-or-null>

Allowed initial invocation states:

    succeeded
    failed

Allowed initial artifact states:

    promoted
    rejected_at_boundary
    not_created

Allowed initial agent states:

    succeeded
    failed

Initial machine-readable reasons should remain narrow.

Examples:

    success
    model_invocation_failed
    empty_raw_output
    invalid_boundary_count
    boundary_order_invalid
    empty_extracted_artifact

The runtime owns these values.

Models do not choose them.

## Success Case

Example:

    type: agent_outcome
    agent: researcher
    invocation_status: succeeded
    artifact_status: promoted
    agent_status: succeeded
    reason: success
    raw_artifact: <project>/raw/researcher-...
    promoted_artifact: <project>/analysis/researcher-...

## Boundary Failure Case

Example:

    type: agent_outcome
    agent: historian
    invocation_status: succeeded
    artifact_status: rejected_at_boundary
    agent_status: failed
    reason: invalid_boundary_count
    raw_artifact: <project>/raw/historian-...
    promoted_artifact: null

This explicitly states that:

- the model invocation completed
- raw evidence exists
- promotion failed
- no canonical cognitive artifact exists
- the failure reason is known

## Invocation Failure Case

Example:

    type: agent_outcome
    agent: historian
    invocation_status: failed
    artifact_status: not_created
    agent_status: failed
    reason: model_invocation_failed
    raw_artifact: <path if any bytes were preserved, otherwise null>
    promoted_artifact: null

## Storage

For R0.5-004, outcome records should be project-owned run evidence.

Proposed location:

    projects/<project>/runs/outcomes/

This avoids placing operational failure records into canonical institutional
knowledge.

The records describe execution state, not research conclusions.

## Required Sequence

    construct prompt
    ->
    invoke model
    ->
    preserve raw emission if available
    ->
    record invocation outcome
    ->
    validate artifact boundary
    ->
    record artifact outcome
    ->
    promote only on success
    ->
    continue or fail according to existing runtime behavior

The outcome record must be written before the runtime exits on failure.

## Experimental Principle

Do not infer state from absence.

Do not use natural-language model output to decide operational outcome.

Do not require parsing terminal logs to reconstruct failure.

The runtime already knows what happened.

The runtime should preserve that knowledge explicitly.

## Causal Control

Baseline:

    malformed output
    ->
    raw file exists
    ->
    analysis file absent
    ->
    terminal reports error

The failure reason must be reconstructed indirectly.

Experimental condition:

    malformed output
    ->
    raw file exists
    ->
    analysis file absent
    ->
    machine-readable agent outcome explicitly records:
        invocation succeeded
        promotion rejected
        reason

The same underlying failure occurs in both conditions.

Only system-owned durable state differs.

## Success Criteria

PASS requires all of the following:

- every attempted agent receives an explicit outcome record
- invocation outcome is distinct from artifact outcome
- complete agent-operation outcome is separately explicit
- successful promotion is explicitly recorded
- malformed boundary failure is explicitly recorded
- model invocation failure is explicitly recordable
- raw and promoted artifact paths are explicit
- null states are explicit rather than inferred
- failure state is written before runtime termination
- models do not choose operational status values
- no semantic interpretation of model prose determines runtime outcome
- R0.5-003 artifact-boundary behavior remains unchanged
- R0.5-002 durable disposition behavior remains unchanged for successful runs
- operational outcome records do not enter canonical `knowledge/entries/`

## Non-Goals

R0.5-004 does not introduce:

- retries
- automatic recovery
- workflow resumption
- distributed execution
- scheduling
- generalized event sourcing
- provenance sidecars
- model-generated failure explanations

Those may be considered separately later.

This experiment records what happened.

It does not yet decide how the institution should recover.

## Architectural Principle

The runtime should never know an important operational fact that the durable
record forgets.

## Status

Experiment defined.

No runtime implementation yet.

## Post-Promotion Failure

An artifact may successfully pass R0.5-003 promotion while later
agent-specific runtime validation fails.

Example:

    invocation_status: succeeded
    artifact_status: promoted
    agent_status: failed
    reason: invalid_judge_disposition

This is not an artifact-boundary failure.

The cognitive artifact exists, but the complete institutional operation did not
succeed.

The same distinction applies to Archivist durable-memory validation.

Therefore successful artifact promotion must never be treated as equivalent to
successful completion of the agent operation.

## Deterministic Experimental Result

The runtime mechanism passed deterministic validation.

Tests demonstrated four distinct operational cases:

1. successful invocation, artifact promotion, and agent completion
2. successful invocation with artifact-boundary rejection
3. model invocation failure before artifact creation
4. successful artifact promotion followed by agent-specific failure

A fifth control demonstrated that an Archivist agent operation can fail after
artifact promotion while the existing Council runtime continues to Librarian.

Outcome records were written before terminating failure paths exited.

The tests confirmed that:

    invocation outcome
    artifact outcome
    complete agent-operation outcome

are distinct system-owned states.

No natural-language inference was required to recover those states.

R0.5-003 artifact-boundary behavior remained functional.

R0.5-002 durable-disposition behavior remained functional when its Judge
operation succeeded.

# R0.5-008 Concurrent Resumer Exclusion

## Question

Can the Research Council guarantee that at most one process may resume a given
interrupted run at a time?

## Motivation

R0.5-007 established safe resumption for one process.

A remaining race exists if two processes concurrently execute:

    ./scripts/run-council.sh --resume <project> <run_id>

Both processes could observe:

    run_status: interrupted

before either changes it.

Without exclusion, both could then:

- mark the same run running
- restart the same interrupted agent
- write the same outcome path
- write competing raw or analysis artifacts
- duplicate Judge or Archivist actions
- race on the final run record
- corrupt run counters or durable state

Therefore:

    safe single-process resume
    !=
    safe concurrent resume

## Required Property

For one logical run:

    at most one live resumer

A second concurrent resumer must fail before it mutates durable run state or
invokes a model.

## Proposed Mechanism

Use a per-run operating-system advisory lock.

Conceptually:

    runs/resume-<run_id>.lock

The runtime should acquire an exclusive nonblocking lock before resume-state
validation or mutation proceeds.

The lock should be associated with an open file descriptor rather than inferred
from the mere existence of the lock file.

Therefore:

    lock file exists
    !=
    lock is held

## Lock Lifetime

The successful resumer retains the lock for the lifetime of the resumed
process.

The operating system releases the lock when that process exits.

This includes ordinary exit and process termination.

The mechanism should therefore not require stale-lock-file deletion to infer
whether a resumer still exists.

## Blocked Resumer

A second process attempting to resume the same run while the lock is held must:

- fail immediately
- not invoke the model
- not alter run state
- not alter counters
- not alter outcomes
- not create promoted artifacts
- not create institutional side effects
- not create a final run record

The blocked process is not a Council-run failure.

It is a rejected competing execution attempt.

## Run-State Semantics

R0.5-008 should not add a new Council run status merely because a competing
resumer was rejected.

The authoritative logical run remains owned by the process that acquired the
lock.

## Process Exit

The blocked competing process should return a distinct nonzero exit code.

Initial candidate:

    75

corresponding to a temporary execution conflict.

The exact shell exit code is operational metadata, not Council institutional
state.

## Scope

The initial mechanism applies to:

    --resume

It does not attempt to serialize independent new runs.

## Causal Control

Baseline:

    interrupted run
    + two concurrent resumers
    ->
    possible duplicated execution

Experimental condition:

    interrupted run
    + first resumer holds exclusive lock
    + second resumer attempts same run
    ->
    second resumer rejected before model invocation
    ->
    first resumer alone completes logical run

## Success Criteria

PASS requires:

- first resumer acquires the run lock
- second concurrent resumer fails
- second resumer performs zero model invocations
- second resumer does not mutate run state
- second resumer does not create an agent outcome
- second resumer does not create raw or promoted artifacts
- second resumer creates no Judge or Archivist side effects
- first resumer remains able to complete normally
- original run ID remains unchanged
- final run state is coherent
- exactly eleven successful agent outcomes exist after completion
- R0.5-007 safe-resumption behavior remains intact
- R0.5-006 interruption behavior remains intact
- earlier artifact and disposition invariants remain intact

## Non-Goals

R0.5-008 does not provide:

- distributed locking across multiple hosts
- automatic resumable-run discovery
- queueing of competing resumers
- automatic retry of rejected resumers
- serialization of independent new runs
- transactional multi-file commits
- generalized process supervision
- distributed leases

## Architectural Principle

A durable run identity must not have multiple simultaneous execution owners.

## Status

Experiment defined.

No runtime implementation yet.
